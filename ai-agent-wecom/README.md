## 背景：端-边-云协同

本教程源自一套「端-边-云」中控架构的落地经验：

- **端**（ESP32-C3 小电视）：桌面显示设备，只拉取、不聚合。
- **边**（树莓派 Hub）：本地服务，聚合行情/天气、缓存、告警、暴露 HTTP 接口。（可以部署本地AI，接入ai agent后可以接入企微，按需选择）
- **云**（AI Agent+云端API）：理解自然语言意图，例如把「帮我把小电视切到天气模式」翻译成对端侧的具体操作。

本教程聚焦**最上层的接入层**：如何让一个 **AI Agent** 通过**企业微信**这个对话入口，
把「人的自然语言意图」转成「对端侧设备的具体操作」。

```
  人 ──(企微群 @机器人 · 自然语言)──► AI Agent接入企微机器人（理解意图 / 规划）
                                          │
                                          ▼
                                 控制中介机器人 / 服务
                                          │
                                          ▼
                                  ESP32 小电视（端侧执行）
```

> **关键设计：对话入口 ≠ 执行入口。**
> 我们**不让** AI Agent 直接去调端侧设备的 API，而是让**另一个「控制中介」机器人/服务**去执行。
> 理由：对话与控制在企微侧天然隔离（未被 @ 的消息机器人收不到），且职责单一、互不抢指令，更利于解耦+扩展。
> 详见 ③。

## ① 企业微信机器人设置

企业微信的机器人有两种 API 模式，**本教程用「智能机器人 + 长连接」**（最省事，免公网回调）。
以下步骤在**企业微信管理后台**和**企微客户端**里完成，不需要写代码。

### 1. 建应用 / 机器人

1. 登录 [企业微信管理后台](https://work.weixin.qq.com/) → **应用管理 → 机器人**（或「智能机器人」入口，不同版本命名略有差异）。
2. 新建一个**智能机器人**，起个名字（例如你自己的 agent 昵称）。
3. 记下它的 **BotId** 和 **Secret**。
   - ⚠️ **这两个是密钥，只放本地（`.env` / 环境变量），绝不进 git、绝不截图外发。**
   - 如果 Secret 泄漏，在后台**重置**即可。

### 2. 选「API 模式 + 长连接」

- 机器人能力里选择 **API 模式**，并开启**长连接（WebSocket）**。
- 这意味着：**不需要**你提供一个公网可访问的回调 URL，**不需要**在企微后台填「可信 IP」。
  - 你的程序主动用 BotId+Secret 连到企微的长连接网关，企微在**消息 @ 了这个机器人**时，
    通过这条长连接把消息推给你。（**网关的具体地址以官方文档为准**。）
- 对比一下另一种模式（**Agent 自建应用模式**）：那种需要公网回调 + 可信 IP，适合要做**主动推送 / 定时消息**的场景。
  本教程的「对话式接入」用长连接就够了。

### 3. 把它拉进群 / 允许私聊

- **群聊**：把机器人加入你的群。之后只要有人在群里 **@机器人** 发消息，你的程序就能收到。
- **私聊**：在后台/客户端允许用户与机器人单聊。
- **访问控制（强烈建议，别搞错重点）**：机器人默认可能对所有人开放。
  - **私聊**：设**白名单**，只允许你本人。
  - **群聊**：⚠️ **没有"只允许某人"这回事**。`@机器人` 只是**消息路由**
    （决定这句话发给谁，顺便减少误触发），**它不提供身份鉴权** ——
    **群里任何能 @ 到它的成员都能控制设备**。
    真正的边界是**谁能进这个群**：请在企业微信后台**限定应用可见范围**，
    并把群成员控制在你信任的范围内。
  - 具体开关名称各版本不同，**理解意图后自己决定**，别照抄我这里的措辞。

### 4. 验收标准

- 在群里 `@机器人 你好`，你的程序日志里能看到一条**来自该群、来自你**的消息事件。
- 在群里发**未 @ 机器人**的普通消息，程序**收不到**。（这是「对话/控制天然隔离」的基础，务必确认。）

## ② ESP32 用法 + Agent 操作规程

> 📄 **给 Agent 的完整摘要见 [`esp32-agent-brief.md`](./esp32-agent-brief.md)** —— 这是一段**自包含、可整段复制**的中文说明。
> 用法：**把它整段丢给你的 AI Agent**，它就能学会「如何操作这台 ESP32 小电视」。

**给人看的一句话摘要**：ESP32-C3 小电视是个桌面显示设备（时钟 / 天气 / 相册 / 股票），
它**只通过 HTTP 从树莓派拉数据**；控制它的方式只有一种 —— **在群里 @设备机器人 说一句中文指令**
（换模式 / 调亮度 / 换日K或分时图 / 换壁纸）。

> ⚠️ **`@` 要「点选」，不能手打。** 在输入框打 `@` 后会弹出成员列表，**从列表里选中那个机器人**；
> 手打 `@设备机器人` 这几个字只是普通文字，企微**不会**把消息下发给它 —— 群里看着像发了，实际没有任何反应。
而**树莓派是数据聚合侧**，提供行情/天气的干净 JSON 接口（契约见[主仓库 README](../README.md)的**「接口契约」**一节）。

Agent 需要学会的核心链路（**只有一条**）：

```
人：@AI助手 帮我把小电视切到股票模式
AI Agent：理解意图 → 在群里 @设备机器人 说一句中文指令
设备机器人：解析中文 → 转发给设备
ESP32：切屏 → 回一条回执
```

> ⚠️ **Agent 不碰任何接口。** 它只需要会说中文、会看回执。
> 设备机器人背后有一套中文指令解析，**agent 不必知道任何参数名或数字映射** ——
> 让它自己在群里 `@设备机器人 帮助`，就能拿到完整指令表（**以它当场返回的为准**，不必抄）。

→ 完整操作规程（**回执怎么读、指令被丢弃了怎么办**）**见 `esp32-agent-brief.md`**。

## ③ harness 接入（原理 + 一个例子）

### 原理：接入分三件事

任何 harness 接入企微，本质都是这三件事：

1. **注册一个「渠道」**：让 harness 知道「企微」是一个消息来源/去向。
2. **维护长连接 + 收发**：用 BotId+Secret 连上企微长连接网关；收到 @消息 → 交给 agent；agent 的回复 → 发回去。
3. **路由与访问控制**：把消息路由到某个会话上下文；按需做私聊白名单/群 @ 门槛。

具体到你的 harness，做成什么形态（插件 / 中间脚本 / 内置 channel）由你自定。**不要假设必须有一个「桥接脚本」**——
在很多框架里，连接是**由主进程内置的 channel 持有的**，根本不需要单独的桥接进程。

### 一个最小例子（伪代码，不绑定任何具体框架）

以下是**原理性伪代码**，展示「收消息 → 交给 agent → 发回」的骨架。请按你的 harness 适配：

```python
# —— 概念示意，非可直接运行代码 ——
bot = WeComBot(bot_id=BOT_ID, secret=BOT_SECRET)   # 用凭证建长连接客户端

@bot.on_message                                    # 收到「@机器人」的消息时
def handle(msg):
    if msg.chat_type == "group":
        text = strip_at_mention(msg.text)          # 去掉正文里的 @机器人 前缀
    else:
        if msg.from_user not in ALLOW_FROM:        # 私聊白名单
            return
        text = msg.text

    reply = agent.handle(text, session_key=msg.session_key)  # 交给 agent（同一群+同一人=同一会话）
    bot.reply(msg, reply)                          # 把回复发回去

bot.run()  # 维持长连接、心跳
```

**要点**：
- `session_key`：建议用 **渠道 + 会话 id（群 id / 用户 id）** 组合，保证同一群同一人对话上下文连续。
- `strip_at_mention`：企微 @机器人 的表述可能混在正文里，注意清理后再喂给 agent，否则会影响命令识别。
- 加一个**「控制中介」**：agent 判断出「这是要操作端侧设备」时，**发指令给你的控制中介**（另一个机器人或本地服务），
  由中介去执行（见 ②）。**不要让 agent 自己直接调设备 API**。

### ⚠️ 这条链路里最容易漏掉的一环（务必先想清楚）

「让 Agent 去 @ 设备机器人」说起来一句话，但**实现上有三个坑**，上面的伪代码里看不出：

1. **Agent 用什么把指令真正送进群？**
   ⚠️ **在回复文本里写「@设备机器人 切换时钟模式」，并不自动等于发出了一条 @ 消息。**
   `@` 在企微里通常是**结构化的提及实体**，不是纯文本。你需要一个**能真正发消息、
   并带上提及实体的工具/能力** —— 而不是让 Agent 把 `@xxx` 当普通文字打印出来。
   具体做法取决于你的 harness（有的框架自带"发消息"工具，有的要在 channel 层做）。
2. **设备机器人的回执怎么回到 Agent 的上下文里？**
   设备机器人**不会 @ 你的 Agent** —— 它只是往这个群发了条消息。
   而企微服务端**只把「@ 了你」的消息下发给你**，所以**默认情况下 Agent 看不到那条回执**。
   ⚠️ 这不是配置没调好，是**协议层的隔离** —— 换哪个框架都一样。
   常见三条出路（按落地难度排序）：

   | 方案 | 做法 | 代价 |
   |---|---|---|
   | **① 读落盘**（最稳、最省事） | 让中介把**每条指令与它的结果落到日志 / SQLite**，Agent 下次被 @ 时自己去读 | 需要约定"去哪读" |
   | **② 中介回执时 @ 你** | 让中介执行完的回执里带上 `@你的Agent` —— 它就成了一条"触发帧"，自动进你的上下文 | 群里多一次机器人往返；要中介配合 |
   | **③ 真推送** | 改用「自建应用 + 公网回调」模式做主动推送 | 需要公网回调 + 可信 IP，家庭宽带/热点下成本高 |

   **本项目实际用的是 ①**：中介照常自己在群里回执（给人看），
   同时**把每条指令与结果打进日志**，Agent 自己去读。
   （所以图里那个 Agent 才能说出"天气那条被设备忙丢弃了" —— 它是**读出来的**，不是从群里看来的。）

   > **②「中介回执时 @ 你」本项目没有实现**，而且它有个前提得先验证：
   > 坑 1 说的"结构化提及实体"，在**机器人之间**也得成立才行 ——
   > 中介在回执正文里写 `@你的Agent`，如果那只是普通文字，同样不生效。
   > 所以 ② 不是"配上就行"，先确认你的中介有没有**发出带提及实体的消息**的能力。
3. **怎么把「回执」对应到「我正在做的那一步」？**
   最省事的办法是**串行**：一次只发一条、等到回执、再发下一条。这样"上一条回执"
   天然就是你正在等的结果。**这也是操作规程里要求"不要连发"的另一个理由。**

   **但串行仍有盲区** —— 回执可能**丢**、可能**乱序**，一旦发生你就对不上"这是第几步的回复"。
   所以本仓库额外支持**业务 ID**：指令里带一个 `[t-7]`，中介会把**同一个 ID 原样带回**：

   ```
   → @设备机器人 [t-7] 切换到日K图
   ← ✅ [t-7] 已切换到日K图
   ```

   于是"哪条回执对应哪一步"变成**显式**的，不再依赖顺序。三条使用纪律：

   - **ID 按「步骤」唯一，不要拿同一个 ID 发不同指令。** 中介只认 ID、**不比对指令内容**：
     同一个 ID 在 60 秒内再来一次，**哪怕内容不一样**也会被判为"重复下发，未再次执行"，
     而回执里的文字是**第一次**那条的。
   - **重复回执仍然是 `✅`，这是故意的** —— 它报的是**那一步的结果**（成功），不是"这次又执行了一遍"。
     收到 `✅ …（重复下发，未再次执行）` 说明**你要的那步早就成功了**，别再重试、更别换方案。
   - **不带 ID 的指令行为完全不变**（比如人手动在群里打的），回执也不会多出方括号。

   > 这个 ID 是**可选的**：不用它照样能跑，只是"回执 ↔ 步骤"的对应退化成**靠顺序猜**。

> 这三条**没有通用答案**，必须落到你自己的 harness 上。我们只把"必须解决什么"讲清楚，
> 具体怎么实现交给你和你的 agent。

### 可选：上下文余量提示

如果你想让 agent **每条回复自动附上「上下文占用/剩余」**（方便知道何时该压缩上下文），
大多数 harness 都有「**发送前 hook**」之类的扩展点：在消息投递前，读当前会话的 token 用量并拼一段 footer。
例如：

```
📊 上下文 20% (40.3k/200.0k) · 余 159.7k
```

实现要点：**在进程内改 payload、不额外调用模型**（近乎零成本）。
